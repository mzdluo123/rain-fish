# AGENTS.md

Bun + TypeScript. Pi-based (`@earendil-works/pi-coding-agent`) assistant that reads/writes files in a virtual filesystem stored in SQLite and can never execute code. All bot state lives in one SQLite file.

## Commands
- `bun install`
- `bun start` — REPL. Needs a provider API key or Pi auth in `~/.pi/agent`.
- `bun test` — bun:test; offline, no API key.
- `bunx tsc` — typecheck (`noEmit`; covers `src/`, `test/`).
- `bun run lint` — Biome linter (`biome.json`, lint only, formatter off). Rules that fight the code's idioms are off (`!` after `noUncheckedIndexedAccess`, comma/assign-in-expression one-liners, expression-bodied `forEach`); errors fail, warnings are advisory.

## Layout
- `src/vfs.ts` — `VirtualFs`: a POSIX-like filesystem in ONE table (`files`, migration 0003). No host disk is involved, so there is nothing to escape: paths resolve against `/`, no symlinks. Size quotas (`VfsLimits`) stop the agent from filling the DB. `src/vfs-ops.ts` plugs it into Pi's read/write/edit/ls; `src/tools/vfs-search.ts` has our own `find`/`grep` (Pi's built-ins shell out to `fd`/`rg` on the host disk). `src/vfs-io.ts` + `src/fs-cli.ts` (`bun run fs ...`) import/export between host dirs and the DB.
- VFS path limits: `VirtualFs.normalize` refuses paths over `MAX_PATH_BYTES` (1024, UTF-8) or `MAX_PATH_DEPTH` (32 components) with `EINVAL` (every parent directory is its own row holding the full path, outside `maxTotalBytes`). The agent-facing `mkdir` of `vfs-ops.ts` only validates: Pi's `write` calls it before `writeFile`, and `writeFile` creates the parents itself, so a refused write leaves no directory rows. `find`/`grep` clamp `limit` to >= 1.
- `src/conversation.ts` — `PiConversation`: persistent per-group conversation with ONE context mechanism, snap compaction (`src/context/`: `estimate.ts`, `archive.ts` = snapcompact wrapper + what is kept out of the archive, `persona.ts` = the pinned profile); there is no level-1 pruning any more: pictures are scaled down on the way in, the profile is pinned outside the history, so nothing is cleared from the live transcript; `src/conversation-store.ts` persists it; `src/conversation-factory.ts` wires model + fs + store + conversation; `src/model.ts` resolves `MODEL`.
- `src/agent.ts` — `createAgent({systemPrompt, fs, store, model?, modelRuntime?, thinkingLevel?})`: tool allowlist, disabled extensions/skills/context files, in-memory session, system prompt = the text passed in `AgentDeps.systemPrompt`.
- `src/index.ts` — CLI REPL.
- `src/store.ts` — `MessageStore(db)` (insert idempotent per platform+group+message id; FTS5 + BM25 `search`). `src/db/open.ts` `openDb(path)` opens the single SQLite file (WAL, migrations) shared by everything.
- `src/db/` — `migrate.ts` (forward-only migrator, `schema_migrations` table, per-migration `BEGIN IMMEDIATE`), `migrations/` (append-only list in `index.ts`), `tokenize.ts` (`Intl.Segmenter` word split; FTS5 index stores space-joined tokens).
- `src/types.ts` — **every shared type lives here** (storage, migrations, virtual fs, core messages, wire types). Wire types are `z.infer` of the schemas; add new types here, not in the module that uses them.
- `src/qq/` — the WebSocket edge. `schemas.ts` (Zod: segments, events, API req/resp), `frame.ts` (`parseFrame`: raw text -> validated `Frame`, never throws), `convert.ts` (validated event -> core `GroupMessage`), `client.ts` (`OneBotClient`: this program is the WS *client*; reconnect/backoff, `send_group_msg` with echo-matched responses and timeouts; `idleTimeoutMs` is armed when the socket is created, so a connection attempt that never opens is closed and retried).
- Pokes (`notice`/`notify`/`poke` with a `group_id`): `parseFrame` -> `Frame` `group_poke` -> `toPokeMessage` turns a poke AT THE BOT (target missing/null counts as the bot) into an ordinary addressed `GroupMessage` (text `[戳一戳] 戳了你一下`, synthetic id `poke-<time>-<user>`, poker named by QQ number because the notice has no nickname); pokes at others, the bot's own pokes and private pokes are dropped. The core sees nothing special: it is stored, queued and answered like a message.
- `src/bot.ts` — core: stores every group message, queues every non-self message to the responder (flag `addressed` = @-mention or reply to a bot message), and owns `sendText` (split long text, quote, remember sent ids), which is what the agent's `send` tool calls. A `reply_to` that is not a numeric QQ id (a poke's synthetic id) is dropped (`quotable`) and the text is sent unquoted, since the outbound schema rejects it. It never answers by itself. Depends only on `GroupMessage`, `QQApi`, `GroupResponder`.
- `src/backfill.ts` — startup history backfill (`backfillGroup`/`backfillAll`) over the `QQHistoryApi` that `OneBotClient` implements (`get_group_msg_history`, `get_group_list`); run from `qq-bot.ts` on the first connection. Only stores messages; never notifies the responder.
- `src/responder.ts` — `PiResponder`: one Pi session per group. Messages queue per group and the agent is woken once the chat has gone quiet, then gets the whole batch in one prompt. When: `src/wake-intensity.ts` keeps a Hawkes excitation per group (`S`, last update; each message adds `weighMessage`: the keyword table and optional `timing` overrides live in the agent's own `/wake-rules.yaml` (`src/wake-rules.ts`: optional `timing:` `{chat_mean_seconds, addressed_mean_seconds, decay_per_second, quiet_threshold}` + YAML list `rules:` of `{name, weight, contains[], starts[], ends[], max_len?, special?}`, parsed with `Bun.YAML` (it rejects alias bombs) and a zod schema; plain substring tests, rules multiply, clamp 0.2–4; seeded from `DEFAULT_RULES` if missing, which also deletes the legacy `/wake-rules.md` table; re-read per message and re-parsed when the text changed; the agent's write/edit of that path is refused by `assertAgentWritable` unless `parseWakeRulesFile` accepts it, and a file broken from outside keeps the last good rules; text is only inspected, trace gets rule names), it decays at `WAKE_DECAY_PER_SECOND` or `timing.decay_per_second`), the wake-up is due after `ln(S/WAKE_QUIET_THRESHOLD)/β` plus an exponential reaction time (`WAKE_CHAT_MEAN_SECONDS`, `WAKE_ADDRESSED_MEAN_SECONDS` once an addressed message is pending, or their `timing` overrides); every message recomputes it, bounded by `WAKE_MAX_WAIT_SECONDS` / `WAKE_ADDRESSED_MAX_WAIT_SECONDS` / `WAKE_MAX_BATCH`. Restored messages start a clock but add no excitation. Every `SPEAK_EVERY_RUNS` successful runs the next batch gets `SPEAK_NOTICE` (`context/nudge.js`) appended at the very end of the user turn (append-only: the prompt-cache prefix is untouched) and a failed `send` there triggers one reminder turn; the per-group count is persisted in `speak_state` (`speak-store.ts`, migration 0006). Runs of a group are serial; a failed run drops its batch.
- Legacy wake rules: seeding `/wake-rules.yaml` deletes `/wake-rules.md` and rewrites `](/wake-rules.md)` to `](/wake-rules.yaml)` in `/persona.md` (host-side write), so the pinned profile has no dead link; the old table is not converted (the agent's tuning resets to the defaults, logged at warn).
- `CACHE_RETENTION` (default `long` = 1 hour prompt cache, `short` = provider default): `bootstrap()` copies it into Pi's `PI_CACHE_RETENTION` (`applyCacheRetention`), which Pi reads per request; the 1-hour tier is only used by providers/models that support it.
- `src/logger.ts` (consola; fancy on TTY, timestamped plain lines when piped) and `src/bootstrap.ts` (shared startup). `src/qq-bot.ts` — entry for `bun run bot` (wires client + bot + responder). `src/config.ts` validates env with Zod (`QQ_WS_URL`, `QQ_TOKEN`, `QQ_GROUPS`, `DB_PATH` default `data/bot.db`).
- Console command (`bun run bot`, stdin lines): `compact` archives the whole live context of every group at once (`PiResponder.compact` -> `PiConversation.compact`; queued behind a running turn of that group, so it never overlaps one). No memory-flush turn runs first.
- Console command `clear` forgets the whole context of every group (`PiResponder.clear` -> `PiConversation.clear` -> `ConversationStore.clear`): live messages AND the archive, in memory and in the DB, in one transaction; the chat log (`messages`), files, persona and `speak_state` stay. Same queueing as `compact`.
- Console command `colab-stop` releases the Colab runtime now (queued behind a run in progress).
- `src/tools/search-messages.ts` — read-only `search_messages` agent tool (part of the allowlist).
- `src/images.ts` — `createImageSource`: the bot (never an agent tool) downloads chat pictures when the agent is woken. `GroupMessage.images` holds only the QQ URLs (photos, stickers and `mface`); `PiResponder` (`attachImages`) fetches the newest `IMAGE_MAX_PER_RUN` (identical pictures of a batch are attached once, sharing a number), only if `Conversation.acceptsImages` (vision model), and passes them to `ask(prompt, { images })` -> `session.prompt(text, { images })`. Fetch rules: https + QQ host allowlist (also on every redirect hop), size cap `IMAGE_MAX_BYTES`, MIME sniffed from magic bytes. A picture that cannot be fetched (expired URL after a restart, too big) stays the `[图片]` text. A picture enters the context ONCE: `attachImages` walks the batch's distinct stored pictures newest first, scales each only when looked at, and skips those whose `imageKey` (sha256 of the scaled bytes, `context/image-key.ts`) is already in `Conversation.imagesInContext()` (the live transcript's user/tool-result image blocks, also after a restart); skipped ones are returned as `repeated` and `formatBatch` names their ids in one `<system>` line (the `<message>` keeps `image_ids`), and they do not use up `IMAGE_MAX_PER_RUN` slots. Compaction drops pictures (snapcompact serializes user text only), so after it a picture may be attached again.
- Order inside `PiResponder.run`: `Conversation.prepare(estimate)` FIRST runs the start-of-run housekeeping (budget reset, persona refresh, cache-expiry compaction or clear fallback, memory flush, threshold compaction), THEN the responder re-reads `imagesInContext()` and decides attached vs repeated, then `ask(prompt, { images, prepared: true })` (which skips the housekeeping). Deciding repeats before compaction would announce pictures that compaction just dropped. `createAgent` turns Pi's image `autoResize` off so the bytes stored in the transcript are the ones we scaled (same `imageKey`); with `IMAGE_MODEL_MAX_PIXELS=0` originals go out unscaled. The cache-expiry clear keeps the run's trace keys (`cur`); only the console `clear` resets them.
- Shutdown (`qq-bot.ts`): `PiResponder.halt()` runs first (cancels wake timers, starts no run, and never calls `pending.remove` again, so `restore()` replays every batch not finished before the halt; a batch answered during shutdown may be answered twice), then `client.stop()`, then `colab.shutdown()`. A second SIGINT/SIGTERM exits at once with code 1.
- `src/tools/send.ts` — `send(text, reply_to?)` and `send_image(image_id?, artifact_path?, text?, reply_to?)`: the only ways the agent speaks; they post to its own group via `SendFn`/`SendImageFn` in `AgentDeps`. Both can be called several times per run and do NOT end it: `src/tools/stop.ts` `stop` returns `terminate: true`. Pi ends the loop only if every result of a tool batch has `terminate`, so `createAgent` wraps `agent.afterToolCall`: a batch whose assistant message contains `stop` ends together (`[send, send, stop]`), unless a call in it failed. The three tools are `executionMode: "sequential"` (a batch containing one runs in call order; pure read batches stay parallel). `src/run-budget.ts` `RunBudget` caps messages per run (`SEND_MAX_PER_RUN`) and paces them (`SEND_GAP_MS`); `PiConversation.ask` resets every per-run cap (`budgets` dep: `RunBudget` and `PythonRunCount`) per run and per reminder turn. Plain model text is never delivered; if a batch was addressed and the turn had no successful `send`/`send_image` (`SPEAK_TOOLS`), `PiConversation.ask` runs one reminder turn (`context/nudge.ts`). The memory-flush turn does NOT change the tool list (that would invalidate the prompt cache): `PiConversation` mutes the `RunBudget` (`speech` dep, `mute()`/`unmute()` in a `finally`), so `send`/`send_image` answer with a tool error and post nothing.
- `run_python(path, args?, timeout_seconds?, max_output_bytes?, input_files?, output_files?)` (`src/tools/run-python.ts`, only if `COLAB_ENABLED`): runs ONE `.py` file of the VFS on a Google Colab CPU runtime; nothing runs on this host. `args` become the script's `sys.argv[1:]` (at most `PYTHON_MAX_ARGS` = 32, `PYTHON_ARGS_MAX_BYTES` = 8 KiB together, no NUL); stdin stays closed. `src/colab/runner.ts` `ColabRunner` owns the one runtime shared by all groups: created by the first run (`colab new`), every run goes through one serial queue (with the idle stop and the startup clean-up), released (`colab stop`) after `COLAB_IDLE_SECONDS` without a run, on shutdown and by `colab-stop`. `colab_runtime` (`src/colab-store.ts`, migration 0008) is written BEFORE `colab new`, so `restore()` at startup reuses a runtime used within the idle time and releases anything else. `src/colab/cli.ts` spawns the `colab` CLI with a fixed argv (config values only, no shell), stdin closed unless code is piped; `src/colab/payload.ts` builds the code sent to the kernel: the file name, source and script arguments travel as base64 JSON (the arguments reach `Popen` as a list after the script name: no shell, never options of `python`), the script runs as its own `python` process (fresh temp dir, own process group, stdin closed) with a wall-clock timeout that kills the group; head + tail of stdout/stderr (`COLAB_OUTPUT_MAX_BYTES` per stream, or the call's `max_output_bytes`, capped at `PYTHON_OUTPUT_MAX_BYTES` = 64 KiB; it all enters the context, the rest is never kept) come back as one `<marker><json>` line (random marker per run, validated with zod). No result line = the session is gone: released, recreated once, retried once. A local kill (CLI past timeout + grace, or abort) is followed by `colab restart-kernel`. Caps: `COLAB_EXEC_MAX_PER_RUN`, `COLAB_EXEC_MAX_PER_HOUR`, `COLAB_EXEC_MAX_TIMEOUT_SECONDS`. `createAgent` blocks `run_python` in a batch that also calls `write`/`edit`. Output is escaped (`element`) like member text.
- Colab transfers: `run_python` accepts explicit `input_files` (VFS → relative sandbox paths) and `output_files` (relative sandbox paths → new VFS files under `/artifacts/`). Each direction is capped at 32 files, 1 MiB/file, 4 MiB total (`src/colab/files.ts`). Generated artifacts are an exception to the agent write file-type/10 KiB rules, but never overwrite anything. Outputs are collected with directory fds and `O_NOFOLLOW`, regular file/ownership/link checks, after killing processes and only on successful execution; `VirtualFs.createFiles` commits the batch atomically or rolls it all back. Bytes travel as Base64 and are not printed in tool results. Nothing persists remotely between runs.
- Colab isolation (`src/colab/payload.ts`): the kernel (root) only launches. Every script runs as the unprivileged user `REMOTE_RUN_USER` (`rainfish-run`, created with `useradd` on first use; uid/gid 0 refused) by ABSOLUTE path (a name like `-x.py` is never a `python` option), in its own 0700 dir under the 0711 root-owned `REMOTE_RUN_ROOT` (`HOME` and `TMPDIR` point there); stdout/stderr go to a root-only dir. Before and after every run every process of that uid is SIGKILLed (`/proc` scan, repeated) and its files in `/tmp`, `/var/tmp`, `/dev/shm` are removed, so nothing of one group's run survives into the next. A kernel that is not root fails the run instead of running unisolated. Needs Python >= 3.9 on the runtime. Secrets in `env` (`TAVILY_API_KEY`) are readable by the script; `secretForms` masks them plain, reversed and base64/base64url in both streams, the launcher error and the CLI failure text (and its log line), which is NOT a guarantee. `COLAB_EXEC_MAX_PER_HOUR` counts runs persisted in `colab_exec` (migration 0009, pruned to the last hour), so a restart does not reset it; `COLAB_OUTPUT_MAX_BYTES` is capped at `PYTHON_OUTPUT_MAX_BYTES` (now in `config.ts`).
- `src/image-store.ts` + migration 0007 — `ImageStore`: pictures of group messages kept in the DB (`images` by sha256, `message_images` links; ids are shown to the agent as `i42`). Every read is scoped to a group (a picture is visible only if a message of that group carried it). `src/picture-archive.ts` `createPictureArchive` downloads pictures as messages arrive (`Bot.handleGroupMessage`, in the background, through the guarded `ImageSource`) and evicts least-recently-used ones past `IMAGE_STORE_MAX_BYTES` (also once at startup, in case the cap was lowered). Eviction then runs `incremental_vacuum` + a WAL truncate so the file really shrinks: `openDb` sets `auto_vacuum = INCREMENTAL` before WAL (a pre-existing file is converted once with `VACUUM`); the responder awaits the same capture (so nothing is downloaded twice), puts `image_ids="i42,…"` on `<message>` and attaches the stored copies. `Bot.sendImage` posts a stored picture as an inline `base64://` segment (the outbound schema accepts nothing else: no URL, no host path) and stores the sent message linked to the picture. `src/tools/view-image.ts` `view_image(image_id)` returns the picture as an image block (needs a vision model; it does not check whether the picture is already in the context). `search_messages` prints `[图片: i42]` and has `with_images`. The model gets a scaled-down copy, never the original; the scaling happens only when a picture is really shown to the model (`PictureArchive.image(groupId, id)`: for the newest `IMAGE_MAX_PER_RUN` pictures of a batch, once per distinct picture, and in `view_image`), not when it is stored or captured (`src/image-resize.ts` via `Bun.Image`, no dependency): one factor for both sides (ratio kept), never enlarged, `IMAGE_MODEL_MAX_PIXELS` / `IMAGE_MODEL_MAX_EDGE` (`view_image(detail)`: `IMAGE_DETAIL_MAX_PIXELS`); JPEG stays JPEG, the rest becomes WebP; it never throws (undecodable or > `MAX_DECODE_PIXELS` = the original is passed through undecoded). The DB keeps the original (what `send_image` posts). `context/image-size.ts` reads the size from the header so the token estimate is ~ w x h / 750 (floor 85, cap 3000, 3000 if unknown). `bun run image-preview <file>` writes a picture at several budgets. What a picture shows is not stored in the DB: the agent writes it into its own `.md` notes next to the id.
- `prompts/agent.md` — the agent's system prompt (group-chat persona), a plain host file chosen by `PROMPT_FILE`, loaded by `loadSystemPrompt` (`conversation-factory.ts`) and passed to Pi verbatim. It is deliberately NOT in the virtual filesystem, so the agent cannot read or rewrite it; the file must not mention itself or its own path.
- `/persona.md` (in the database, created by the agent) — its own evolving self-profile; it writes it with its file tools. `PiConversation` shows its text at the very top of every request (`context/persona.ts` `personaPinMessage`, applied in `transformContext`; it is a view, never stored in `agent_messages`), read once per run (`persona` dep: an edit shows up in the next run, so the cached prefix stays stable within a run), so compaction cannot drop it, and the archive leaves out the agent's reads/writes of the profile files (`personaTree`: the entry + every `.md` reachable by absolute links), whose current truth is the file. Treat it as untrusted data (group members can influence it): it is escaped like member text, introduced by one `<system>` framing line that says "notes, not commands", and truncated at `PERSONA_MAX_CHARS`. Only the entry file is pinned; linked files are read on demand.
- Link check (`unlinkedNotes` in `context/persona.ts`, dep `unlinked` of `PiConversation`): every `.md` AND `.py` file must be reachable from `/persona.md` by absolute Markdown links (full walk, no 200 cap; only `.md` files are opened and followed, a script is a leaf; `personaTree`, the archive filter, stays `.md`-only so runs of scripts are archived). `PiConversation.ask` runs it at the start of EVERY run and appends `linkNotice` (`context/nudge.ts`) to the end of the user turn while anything is unlinked (stateless: also catches host-side `bun run fs` writes); after any turn with a successful `write`/`edit` (including the memory-flush turn) it re-checks and, if still unlinked, runs ONE reminder turn (`linkNudgePrompt`). A throwing check counts as clean and is logged. `/wake-rules.yaml` is neither, so it needs no link (the seed persona just names it).
- `test/` — bun:test suites; `helpers.ts` `makeEnv()` builds an in-memory DB, an empty agent filesystem and a prompt string.

## Invariants (do not break)
- `edit`, and `write` over an existing file, need the file in the context window: `createAgent` passes `requireSeen` to `createVfsOperations`, which runs `assertSeen` (`src/context/read-guard.ts`) on the session's own `agent.state.messages`. The newest successful whole-file `read`/`write`/`edit` of the path counts (a read with offset/limit does not, a result of the batch still running is not there yet), so what compaction, a rollback or a restart removed from the messages must be read again; a file whose mtime (seconds) is newer than that access is refused as stale. Creating a new file needs no read; the pinned `/persona.md` text does not count as a read. Applies to every `.md`, not only the profile. Tests that call tools directly use `markSeen` (`test/helpers.ts`).
- `/wake-rules.yaml` is agent-writable input that steers scheduling, so its power stays bounded in code: no regex, `MAX_RULES`, per-weight and product limits, bounded optional `timing` fields (`chat_mean_seconds`, `addressed_mean_seconds`, `decay_per_second`, `quiet_threshold`), and the wake-up always ends by `WAKE_MAX_WAIT_SECONDS` / `WAKE_ADDRESSED_MAX_WAIT_SECONDS` / `WAKE_MAX_BATCH`. Do not let it set those, and keep the validation in `assertAgentWritable`.
- `bash` must never be enabled. `ALLOWED_TOOLS` in `src/agent.ts` is the allowlist, and startup throws if any other tool is active. The host NEVER executes code the agent wrote: do not add tools that evaluate code locally, or that touch the network or the host disk. The one exception to "no processes, no network" is `run_python`: it spawns only the `colab` CLI, with an argv built from config (never from agent input), no shell, and the code goes to the remote Colab kernel on stdin; it takes a VFS path only and reads through `VirtualFs`. Never call `colab auth`/`colab drivemount` (the runtime must hold no credentials). `view_image` takes an id only and reads through `ImageStore.get(groupId, id)`. `send_image` takes exactly one of a group-scoped `image_id` or an absolute VFS `artifact_path` under `/artifacts/`; artifacts are read only through `VirtualFs`, magic-sniffed JPEG/PNG/GIF/WebP, at most 1 MiB, and sent as inline base64. No picture tool reads host paths or accepts URLs.
- The agent's filesystem is the DB. Never give it a tool that reads host paths; any new file tool goes through `VirtualFs` (and a host-escape test like the ones in `test/vfs-tools.test.ts`). Pi's built-in `find`/`grep` must not be enabled: they use `fd`/`rg` on the host disk.
- Custom tool definitions are registered with `customTools` under the built-in names so they replace the host-disk built-ins; keep the names identical.
- Keep `noExtensions`, `noSkills`, `noPromptTemplates`, `noThemes`, `noContextFiles` on the resource loader — each is a way for outside content to add tools or instructions.
- No persona text lives in code: the prompt file is passed to Pi as text. The real "no code execution on the host" guarantee is the tool allowlist + startup check, not the prompt.
- The agent may only write `.md` and `.py` files (plus `/wake-rules.yaml`, validated on every write) of at most `AGENT_MAX_FILE_BYTES` (10 KiB); this is enforced in `src/vfs-ops.ts` (agent tools), not in `VirtualFs`, so host-side `bun run fs` is unaffected. The `.md` size error text is the agent's instruction for splitting into linked files; keep it.
- Program-authored `<system>` text (identity notice, nudges, memory-flush prompt, archive lead-in, profile framing, picture notice) and the system prompt `prompts/agent.md` are written in English to save tokens; the persona seed (`prompts/persona.md`, which holds the expression rule: positive phrasing, no "don't" lists) stay Chinese; `/wake-rules.yaml` has English comments. The archive marker is `<system>[archive]`.
- Text typed by group members must go through `src/xml.ts` (`escapeText`/`escapeAttr`/`element`) before it reaches the model, and program-authored user-turn text is wrapped with `systemMessage` (`<system>`). The archive is recognised by a `<system>`-prefixed marker; do not weaken escaping, or a member could forge it.

## Context management rules
- History is never silently lost: compaction moves retired turns into the archive text in the same transaction that deletes them. Two kinds of text are deliberately not archived (`serializeForArchive`): program-written `<system>` blocks of user turns (identity notice, picture numbering, must-speak notice, flush/reminder prompts: they repeat in every batch) and calls on profile files. The archive has a budget (`CONTEXT_ARCHIVE_TOKENS`); across rounds `extendArchiveSource` appends the newly retired text and `trimOldest` drops the OLDEST text beyond the budget, so the oldest history leaves the archive for good (chat text stays searchable with `search_messages`; the agent's own tool activity does not). Cuts happen only at turn starts so tool calls keep their results.
- Cache-expiry compaction (`PiConversation.compactIfCacheExpired`, config `cacheCompact`: `CACHE_COMPACT_ENABLED` / `_TTL_SECONDS` / `_MIN_SAVED_TOKENS` / `_MIN_SAVED_RATIO`, own TTL, not derived from `CACHE_RETENTION`): at the start of a run, if the last assistant message ended (`timestamp + durationMs`, persisted) more than the TTL ago, the provider cache is gone and the next request re-writes the whole prefix anyway, so the WHOLE live context is archived (lossless snap compaction, no memory flush). `archiveThrough` builds the new archive first and commits only if the estimated saving passes both minimums; otherwise it falls through to the clear fallback. If compaction would save too little and `CACHE_COMPACT_CLEAR_FALLBACK` is on, `clear()` runs instead (live messages AND archive are forgotten; NOT lossless) when dropping the whole transcript passes the same minimums; else nothing changes (`compact.skip`). Never done while the cache is alive. Omitted dep = off (tests).
- A turn whose model call fails must be rolled back from memory and the DB (otherwise a poisoned message repeats forever).
- Pi's own compaction stays disabled (`createAgent` sets `compaction.enabled=false`); do not enable both. Pi's image `autoResize` stays off too (see the `PiResponder.run` ordering above).
- Thresholds live in `configSchema` + `.env.example`; `recent + archive < compact` is validated. The archive lead-in in `context/archive.ts` is protocol framing, not persona; persona text stays in `prompts/agent.md`.
- `@oh-my-pi/snapcompact` needs Bun >= 1.4.4 and native binaries (`@oh-my-pi/pi-natives`); it types messages with omp's pi-ai, so `serializeForArchive` casts our Pi messages (same shapes).

## Logging and configuration rules
- No `console.*` in `src/`. Components receive a `Logger` (type in `types.ts`) via their options and default to `noopLogger`; entry points get one from `bootstrap()` (`src/bootstrap.ts`: loads + validates env, builds the logger, exits with a readable error on bad config). Levels mean something: `debug` per-message/tool detail, `info` lifecycle, `success` completed actions, `warn` recoverable/dropped input, `error` failures.
- Never log secrets (`QQ_TOKEN`, API keys) or full message bodies above `debug`.
- Config: add the variable to `configSchema` (`src/config.ts`) AND `.env.example`. Empty values count as unset. Bun loads `.env` itself; do not add dotenv.
- Tests use `recordingLogger()` from `test/helpers.ts` to assert on level + message.
- Structured trace: components get an `EventLog` (`types.ts`) via options and default to `noopEventLog`; `bootstrap()` builds the real one (`src/trace/`: `event-log.ts` JSONL + `rotating-file.ts` rotation/retention, `session-events.ts` maps Pi session events). Event names are `domain.action`, fields snake_case, correlation keys `group`/`run`/`turn`/`call_id`. `emit` must never throw. Without `TRACE_CONTENT`, record sizes/ids/names only: use `preview()` for any text and `summarizeArgs` for tool arguments. A change to a field's meaning bumps `EVENT_SCHEMA_VERSION`. State transitions (`group.state`, `conv.state`) must name their `reason`.

## Edge validation rules
- Raw WebSocket data is untrusted. It is parsed only in `src/qq/frame.ts`/`client.ts` with the Zod schemas; the core (`bot.ts`, `responder.ts`, `store.ts`, tools) must never import from `qq/schemas.ts` or see a wire event.
- Outbound requests are validated too (`sendGroupMsgRequestSchema`) before being sent. Responses to our requests are validated before use.
- Unknown segment types / malformed segment data degrade to `{type:"unknown"}`; a malformed *event* is dropped and logged, never partially processed.
- New event type needed? Add its schema in `schemas.ts`, a `Frame` variant in `types.ts`, a branch in `parseFrame`, and tests in `test/frame.test.ts`.

## Database rules
- Schema changes = new file in `src/db/migrations/` + append to `migrations/index.ts`. Never edit or renumber a shipped migration. Migrations run in a transaction; use `up(db)` for data backfills too (see 0002).
- The agent must never get a path to the DB file or a raw SQL tool. Search queries are tokenised and quoted before reaching FTS5; keep it that way.
- Changing `tokenize()` changes what is indexed: ship it with a migration that rebuilds `messages_fts`.

## Gotchas
- Our `grep` runs the agent's regex in-process; a pathological regex can stall the event loop (lines are cut to 500 chars, which bounds but does not remove the risk).
- All state goes in the one SQLite file (messages, files, conversations, the pending-message queue, per-group flags); add new state as a migration, not as another file. Anything the process keeps only in memory is lost on restart: before adding such state, decide whether a restart may forget it (timers and the `PiResponder` queue are rebuilt from `pending_messages` by `restore()`; Pi's own config/API keys stay in `~/.pi/agent`).
- `ToolDefinition` generics are invariant, hence the `as unknown as ToolDefinition[]` cast in `agent.ts`.
- Pi is `@earendil-works/*` (1.x). Model/credential access is the async `ModelRuntime` (`src/model.ts`); `createPiConversationFactory` is therefore async and `orExit` awaits promises. `THINKING_LEVEL` (off..max) is passed to `createAgentSession`.
- Pi sessions are in-memory (`SessionManager.inMemory`); the conversation is restored from `agent_messages`/`agent_archives` by `PiConversation.create`, so nothing Pi-side needs to persist.

- Generated image delivery: `ImageSendSource` carries either an existing picture id or validated VFS bytes through `SendImageFn`/`GroupImageSender`. `Bot.sendImage` stores successful artifact sends with `ImageStore.put` linked to the outbound message; the QQ entry point passes `imageStoreMaxBytes` so generated images obey the configured retention cap.
